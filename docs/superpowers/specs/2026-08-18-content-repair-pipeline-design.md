# Цикл генерации, проверки и исправления — дизайн

## Цель

Собрать существующие извлечение, генерацию и валидаторы в фиксированный
конвейер, который либо возвращает проверенную карточку, либо направляет её на
ручную проверку после ограниченного числа попыток.

## Граница и интерфейс

Публичный контракт остаётся ровно таким, как указан в roadmap:

```python
def run_content_pipeline(
    product: Product,
    llm: LLMClient,
    max_attempts: int = 3,
) -> PipelineResult: ...
```

Новый модуль `marketplace_agent.content.pipeline` будет единственной точкой
координации. Он сам загружает `data/specs/{product.category}.yaml` и
`data/processed/rules.yaml`. В MVP категория `laptops` уже совпадает с именем
файла `laptops.yaml`.

## Поток

1. Один раз извлечь подтверждённые атрибуты из описания поставщика.
2. Построить `GroundingEvidence` из извлечённых непустых атрибутов и исходного
   описания поставщика.
3. На первой попытке вызвать `generate_content`; на следующих — отдельный
   `repair_content`.
4. Проверять карточку в порядке: детерминированные правила, grounding,
   семантические правила.
5. При отсутствии нарушений вернуть `PipelineResult(status="completed")`.
6. При нарушениях сохранить хэш полного JSON карточки. Если хэш уже был,
   вернуть `manual_review` сразу: модель повторяет тот же результат.
7. Если попытки закончились, вернуть `manual_review` с последними
   нарушениями и карточкой.

## Исправление

`repair_content(content, violations, evidence, llm) -> GeneratedContent`
получает текущую карточку, точный сериализованный список нарушений и только
разрешённые доказательства. Промпт требует исправить перечисленные нарушения,
не добавлять факты и вернуть строго `GeneratedContent` JSON.

Grounding-нарушения конвертируются в `RuleViolation` с
`rule_id="unsupported-claim"`, `severity="high"`, полем исходного
утверждения и понятным сообщением. Так все виды нарушений передаются в один
ремонтный контракт и сохраняются в `PipelineResult`.

## Ошибки и состояние

- `max_attempts < 1` вызывает `ValueError` до LLM-вызовов.
- Невалидный структурированный ответ LLM остаётся ошибкой существующего
  `chat_structured`; блок не маскирует его как успешную карточку.
- `failed` пока не используется: его зарезервированный статус нужен для
  будущей обработки ошибок провайдеров. В этом блоке исчерпание попыток и
  повтор карточки всегда дают `manual_review`.

## Тесты

Тесты с `FakeLLMClient` доказывают три сценария:

1. первая генерация проходит все проверки и возвращает `completed` с одной
   попыткой;
2. первая карточка нарушает правило, вторая исправлена и возвращает
   `completed` с двумя попытками;
3. одинаковая карточка повторяется и возвращает `manual_review` до третьей
   попытки.

Дополнительно тестируется предел попыток и передача точного списка нарушений
в запрос исправления.

## Почему фиксированный конвейер

Исходный учебный документ рекомендует для узких задач фиксированный конвейер:
он предсказуемее, дешевле и проще для тестирования, чем агент, самостоятельно
выбирающий шаги. Три попытки и явная ручная очередь задают контролируемую
границу автоматизации.
