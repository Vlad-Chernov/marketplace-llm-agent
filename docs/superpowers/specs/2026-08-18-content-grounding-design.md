# Проверка подтверждённости фактов — дизайн

## Цель

Не пропускать в карточку товара факты, которых нет в подтверждённых
атрибутах или описании поставщика.

## Выбранный подход

Используем два независимых барьера.

1. Код сравнивает `GeneratedContent.used_attributes` с подтверждёнными
   атрибутами. Различие ключа или значения — неподтверждённый факт.
2. Один структурированный LLM-вызов читает `title`, `bullets`,
   `description` и `keywords` вместе с описанием поставщика. Он возвращает
   только атомарные утверждения, которые не подтверждены описанием.

Такой вариант дешевле и надёжнее проверки всех атрибутов моделью, но ловит
свободные текстовые утверждения, которые нельзя извлечь простым сравнением.

## Рассмотренные варианты

- Только LLM: проще на старте, но модель может ошибиться в точном сравнении
  чисел и значений.
- Только код: точно проверяет `used_attributes`, но не видит факты,
  добавленные в обычный текст.
- Гибридный подход: выбранный вариант. Код проверяет структурированные данные,
  LLM — оставшиеся текстовые утверждения.

## Контракты

В `marketplace_agent.validation.grounding` появятся:

```python
class GroundingEvidence(BaseModel):
    confirmed_attributes: dict[str, Any]
    supplier_description: str


class UnsupportedClaim(BaseModel):
    field: Literal["title", "bullets", "description", "keywords", "used_attributes"]
    claim: str
    reason: str


class GroundingResult(BaseModel):
    unsupported_claims: list[UnsupportedClaim]


def validate_grounding(
    content: GeneratedContent,
    evidence: GroundingEvidence,
    llm: LLMClient,
) -> GroundingResult: ...
```

`confirmed_attributes` — единственный источник истины для
`used_attributes`. `supplier_description` — единственное текстовое
доказательство для LLM. Скрытый `true_attributes` в этот модуль не передаётся.

## Поток данных

1. `validate_grounding` добавляет в результат нарушения сравнения
   `used_attributes` с `confirmed_attributes`.
2. Если такие нарушения есть, он сразу возвращает результат: текстовую
   проверку выполнять уже не нужно.
3. Если `used_attributes` корректны, он делает ровно один LLM-вызов со всей
   карточкой и описанием поставщика.
4. Ответ проходит Pydantic-проверку. Если LLM возвращает пустой список,
   текстовые утверждения считаются подтверждёнными.
   LLM-вызов выполняется только если детерминированных нарушений нет.

## Ошибки и ограничения

- Невалидный JSON LLM вызывает существующий `StructuredOutputError`.
- LLM не может вернуть поле вне пяти разрешённых значений: это отвергает
  Pydantic.
- Смысловая проверка ограничена текстом поставщика и может пропустить факт,
  неявно подразумеваемый описанием. Это фиксируется как ограничение будущей
  оценки, но не расширяет MVP.

## Тесты

Тесты должны доказать:

1. несовпадающее значение из `used_attributes` обнаруживается без вызова LLM;
2. неизвестный ключ из `used_attributes` обнаруживается без вызова LLM;
3. специально выдуманный факт в описании обнаруживается одним LLM-вызовом;
4. безопасная карточка возвращает пустой результат;
5. поле вне схемы LLM-ответа отклоняется.

## Граница блока

Блок только обнаруживает и возвращает неподтверждённые факты. Удаление фактов
и повторная генерация относятся к блоку 4.4.
