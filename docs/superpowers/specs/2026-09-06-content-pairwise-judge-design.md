# Дизайн эксперимента: слепое парное сравнение карточек

## Цель

Проверить, воспринимается ли карточка из LangGraph-конвейера лучше карточки
из сохранённого линейного конвейера при слепом сравнении. Эксперимент измеряет
не технические метрики, а предпочтение человека и согласие независимого
LLM-судьи с человеком.

## Набор данных и версии

Используются 50 синтетических товаров, созданных через
`generate_clean_products(count=50, seed=...)` и зашумлённых тем же
воспроизводимым способом, что и набор для content pipeline. Для каждого SKU
отдельно запускаются две версии с одинаковыми моделью, температурой,
`max_attempts=3`, правилами валидации и ценами:

- `legacy-linear-v1` — оценочная линейная реализация;
- `langgraph-v1` — текущий production-конвейер.

На каждый вызов создаётся новый LLM-клиент. Результаты с ошибкой,
`manual_review` или отсутствующей карточкой не попадают в ручной выбор, но
учитываются в технической сводке. Из оставшихся SKU в стабильном порядке
берутся первые 30 пар, где обе версии завершились `completed`. Если 30 пар
не набирается, прогон завершается явной ошибкой без бланка для оценки.

## Слепой бланк

Для каждой выбранной пары создаются:

- `pair_id` вида `PAIR-001`;
- SKU и подтверждённые атрибуты товара;
- карточки `A` и `B`: title, bullets, description, keywords;
- пустое поле `choice`.

Соответствие `A/B` версиям определяется детерминированно от `run_id` и
`pair_id`, чтобы порядок нельзя было подстроить под ожидаемый результат.
В бланк не попадают имя версии, latency, число попыток, нарушения, токены и
внутренние traces. Карточки и атрибуты синтетические, поэтому их разрешено
передать человеку; prompts, ответы модели и ключи не сохраняются.

Пользователь заполняет отдельный JSON:

```json
{"pair_id": "PAIR-001", "choice": "A"}
```

Допустимы только `A`, `B` и `tie`. Каждый из 30 `pair_id` должен встретиться
ровно один раз.

## LLM-судья

После формирования пар отдельный LLM-клиент оценивает те же A/B-карточки в
слепом виде. В запросе есть только подтверждённые атрибуты, A и B, а также
единый рубрикатор:

1. фактическая точность относительно подтверждённых атрибутов;
2. ясность и читаемость;
3. полезность для покупателя;
4. при равенстве — `tie`.

Судья возвращает строгий JSON с `choice` и краткой причиной. Его имя модели,
ошибки и решение сохраняются; текст запроса и ответ модели не сохраняются.
Ошибка судьи фиксируется отдельно и исключается только из метрик согласия,
а не из ручных результатов.

## Метрики и раскрытие вариантов

После ручного выбора выполняется валидация файла и раскрывается соответствие
A/B версиям. Сводка содержит:

- победы legacy, LangGraph и ничьи по ручному выбору;
- победы legacy, LangGraph и ничьи по LLM-судье;
- долю точного совпадения решений человека и судьи;
- Cohen's kappa для трёх значений `A`, `B`, `tie`;
- количество неготовых пар и ошибок LLM-судьи.

Согласие считается только по парам с валидным ручным выбором и валидным
решением судьи. Это измеряет надёжность LLM-судьи, а не истинное качество
карточки; ручной выбор остаётся эталоном эксперимента.

## Артефакты и воспроизводимость

Один запуск создаёт:

- безопасный технический JSON в `evals/runs/` с seed, хэшами входных данных,
  конфигурацией, техническими статусами и итоговыми агрегатами;
- слепой бланк `evals/manual/content-pairs-<run_id>.json`;
- после оценки — JSON ручных решений и итоговый отчёт без скрытого A/B
  соответствия до момента раскрытия.

CLI печатает прогресс обоих конвейеров и LLM-судьи при `LLM_PROGRESS=1`.
Живой прогон запускается вручную, потому что использует внешний провайдер.

## Решение

LangGraph можно считать предпочтительным по восприятию, если его доля побед
выше legacy без существенного роста доли ничьих. Результат признаётся
неопределённым, если доля ничьих велика или Cohen's kappa ниже `0.40`:
тогда LLM-судья недостаточно согласуется с человеком, чтобы использовать его
как самостоятельный показатель.

## Вне scope

- изменение генератора, prompts, правил валидации или production-конвейера;
- повторная оптимизация few-shot;
- автоматическая замена ручного выбора LLM-судьёй;
- сравнение провайдеров из блока 13.4.
