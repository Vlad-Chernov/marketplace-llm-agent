# Спецификация учебного проекта: LLM-агент для маркетплейса

Дата фиксации: 13 августа 2026 года.

Основной источник: [«Пет-проект: LLM-агенты»](</Users/vlad/Documents/Codex/2026-08-10/new-chat-2/outputs/pet_project_llm_agents.docx>).

## 1. Цель

Создать локальную учебную систему для контент-менеджера и категорийного менеджера Ozon-подобного маркетплейса. Система должна:

1. Извлекать характеристики из грязного описания поставщика.
2. Создавать карточку товара только из подтверждённых фактов.
3. Проверять правила площадки и исправлять нарушения.
4. Находить конкретные дефекты в отзывах, считать частоты и динамику.
5. Отвечать покупателям по документам поддержки и данным заказа.

Проект предназначен для обучения и портфолио на позиции LLM/AI Engineer и Data Scientist/ML Engineer. Реальной интеграции с Ozon нет.

## 2. Учебные ограничения

- Первый LLM-проект пользователя.
- Python: средний уровень; API, Git, терминал, pytest и ООП изучаются с нуля.
- Работа на MacBook Air M2 2022 года с 8 ГБ памяти.
- Начальный бюджет на модели и инфраструктуру: 0.
- Работа по 3–4 часа в день, 4–5 дней в неделю, без жёсткого дедлайна.
- Данные и интерфейс — на русском языке. Код, имена сущностей и публичная документация для портфолио (`README.md`, docstrings) — на английском. Учебные файлы управления (`PROJECT_SPEC.md`, `ROADMAP.md`, `DECISIONS.md`, `EXPERIMENTS.md`) — на русском, чтобы пользователь понимал каждое решение.
- Репозиторий GitHub — приватный; публикация возможна перед использованием в портфолио.

## 3. Формат обучения

Каждый блок занимает 45–90 минут и содержит:

1. Короткую теорию простыми словами.
2. Точное указание, какую папку или файл создать.
3. Полный код текущего законченного шага.
4. Объяснение важных блоков кода.
5. Точную команду запуска.
6. Ожидаемый результат.
7. Тест и разбор ошибок.
8. Git-коммит с объяснением команды.

Пользователь вручную повторяет действия и пишет «готово» только после успешной проверки. Следующий блок не начинается, пока текущий результат не подтверждён.

## 4. Выбранный подход

Один модульный проект в одном репозитории. Каждая часть сначала создаётся и тестируется отдельно, после чего части объединяются:

1. Генератор синтетических данных.
2. Конвейер обработки карточек.
3. Анализ отзывов.
4. RAG и агент поддержки.
5. Общая оркестрация.
6. Локальная Streamlit-панель продавца.

MVP использует явную оркестрацию на обычном Python. Полная версия добавляет LangGraph и сравнивает конвейер с агентом.

## 5. Границы MVP

MVP должен включать:

- одну категорию — ноутбуки;
- 40 синтетических товаров;
- 200 синтетических отзывов;
- справочник из 12 характеристик, четыре обязательные;
- правила карточек, необходимые для демонстрации детерминированной и семантической проверки;
- небольшую базу документов поддержки и синтетических заказов;
- извлечение характеристик;
- генерацию, проверку и исправление карточки;
- базовый поиск дефектов в отзывах;
- RAG по правилам возврата;
- минимального агента поддержки;
- золотой набор из 25 задач;
- тесты, метрики, логи и учёт стоимости вызовов.

MVP считается законченным, когда весь сценарий работает локально, воспроизводимо запускается по инструкции, а результаты измерены на золотом наборе.

## 6. Границы полной версии

Полная версия должна включать:

- 400 товаров в категориях «ноутбуки», «кроссовки», «электрические чайники»;
- 12 характеристик на категорию, четыре обязательные;
- 4000 отзывов;
- около 20 правил площадки;
- 8–10 документов поддержки;
- 500 синтетических заказов;
- золотой набор из 50 задач;
- пакетную обработку, ограничения конкурентности, повторные попытки, контрольные точки и очередь ошибок;
- очистку персональных данных;
- защиту от prompt injection и доступа к чужому заказу;
- LangGraph-оркестрацию;
- Streamlit-панель продавца;
- итоговые метрики, README, журнал решений и экспериментов.

## 7. Данные

### 7.1 Каталог

Сначала генератор создаёт полный эталон `true_attributes`, затем строит из него грязное описание поставщика и частично заполненные `attributes`. `true_attributes` доступны только генератору и оценочному коду; рабочая система их не получает.

Для полной версии намеренно создаются:

- 40% пропущенных характеристик;
- 10% грязных описаний с капслоком, обрывками HTML и лишними знаками;
- 5% описаний с запрещёнными заявлениями, контактами или ссылками;
- 3% товаров в неправильной категории.

### 7.2 Отзывы

Полный набор имитирует:

- J-образное распределение оценок;
- 40% бесполезных отзывов;
- 15% отзывов с посаженными конкретными дефектами;
- 5% отзывов с персональными данными;
- 3% отзывов про доставку, а не про товар;
- появление дефекта после заданной даты у нескольких товаров.

### 7.3 Ручная работа

Руками создаются и проверяются:

- схемы характеристик категорий;
- правила площадки;
- сложные, запрещённые и adversarial-примеры;
- не менее 60% золотого набора;
- 100 примеров для проверки фильтра персональных данных в полной версии;
- 30 пар старых и новых карточек для проверки LLM-судьи.

## 8. Компоненты и поток данных

### 8.1 Карточки

`true_attributes → грязное описание → extract_attributes → generate_content → validate_content → repair_content`

- Неизвестный атрибут не выдумывается: используется `null`/«не знаю».
- Enum-значения нормализуются по справочнику категории.
- Детерминированные правила проверяет Python.
- Семантические правила проверяет LLM одним пакетным запросом.
- После трёх неудачных исправлений карточка отправляется в ручную очередь.

### 8.2 Отзывы

`отзывы → дедупликация и фильтр мусора → очистка ПДн → классификация/кластеризация → дефекты, частоты и динамика`

Результат обязан содержать числа. Пересказ вида «некоторые жалуются» не считается достаточным.

### 8.3 Поддержка

`вопрос → guardrails → поиск политики и данных заказа → расчёт условий кодом → ответ с цитатой или эскалация`

- RAG используется для документов поддержки.
- Условия возврата вычисляет код, а LLM только объясняет решение.
- При отсутствии номера заказа агент задаёт уточняющий вопрос.
- Доступ к заказу проверяется по идентификатору сессии.
- Если данных недостаточно, агент отказывается от выдуманного ответа.

## 9. Ошибки и безопасность

- Все структурированные ответы проверяются Pydantic-схемами.
- Ошибка инструмента превращается в структурированный результат, а не завершает процесс исключением.
- Действуют лимиты числа шагов, повторов, времени и стоимости.
- Каждый LLM-вызов и вызов инструмента трассируется без API-ключей и персональных данных.
- Прямые и косвенные prompt injection входят в adversarial-набор.
- Простые гарантируемые проверки реализуются кодом, а не LLM.
- Система поддерживает `no_answer` и передачу человеку.

## 10. Оценка качества

MVP использует 25 задач для быстрой обратной связи. Полная версия использует 50 задач со следующим распределением из задания:

- извлечение характеристик — 15;
- генерация карточек — 8;
- проверка правил — 6;
- анализ отзывов — 6;
- агент поддержки — 8;
- `no_answer` — 3;
- adversarial — 4.

Метрики полной версии:

- Attribute F1 ≥ 0.80;
- доля выдуманных атрибутов ≤ 0.05;
- карточек без нарушений ≥ 0.95;
- критических нарушений — 0;
- найдено посаженных дефектов ≥ 0.80;
- Retrieval Recall@5 по политике ≥ 0.85;
- успех агента поддержки ≥ 0.75;
- точность эскалации ≥ 0.85;
- утечек персональных данных — 0;
- скорость и стоимость обработки измерены и объяснены.

Метрики поиска считаются отдельно от качества итогового ответа. Результаты каждого эксперимента сохраняются по каждому примеру, а не только в агрегированном виде.

В 50 задачах сохраняется предметное распределение §4.5. Дополнительно минимум восемь задач (≥15%) помечаются тегом `no_answer`; одна задача может одновременно относиться к предметному блоку и проверять корректный отказ. Так выполняются и таблица кейса B, и общий чек-лист §6.2.

## 11. Технологии

- Python 3.11+.
- `uv` для окружения и зависимостей.
- Pydantic v2 для моделей и структурированного вывода.
- SQLite для локальных данных.
- ChromaDB и BM25 для гибридного поиска.
- Бесплатный облачный LLM API для MVP; провайдер выбирается перед настройкой по актуальным лимитам.
- Два доступных бесплатных провайдера реализуют единый интерфейс и выбираются через `LLM_PROVIDER`; бизнес-логика не зависит от SDK.
- LangGraph только в полной версии.
- FastAPI для одного локального программного API и Streamlit для панели продавца; интерфейс делается после измерения основных модулей.
- Streamlit для локального интерфейса.
- pytest и Ruff для тестов и проверки кода.
- Git и приватный GitHub для истории проекта.

## 12. Что не входит в текущий проект

- настоящий API Ozon;
- копия сайта Ozon;
- реальные данные покупателей и продавцов;
- платный API до подтверждённой необходимости;
- Docker до финальной упаковки;
- онлайн-развёртывание;
- мобильное приложение;
- автоматическое изменение реальных заказов и карточек.

## 16. Критерий общего завершения

Проект завершён, когда:

1. Он локально запускается по README на целевом Mac.
2. Все четыре предметных функции работают и покрыты тестами.
3. Метрики посчитаны на зафиксированном золотом наборе.
4. Ограничения и неудачные эксперименты честно описаны.
5. Пользователь может объяснить архитектуру, основные функции, метрики и причины инженерных решений.
